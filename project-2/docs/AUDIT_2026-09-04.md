# Codebase audit and remediation status

## Scope and conclusion

The repository was a Flask dashboard prototype, not a production betting
analytics system. Its former output must not be used to measure prediction
quality, expected value, or profitability: it contained manufactured training
rows, hard-coded stale team statistics, sample schedules/results, and a route
that intentionally introduced random errors then stored simulations in database
tables named as real predictions and results.

The public app now uses the new `sam_analytics` core and retires the old API
surface with HTTP 410. The old source remains only to make the remediation
reviewable. Do not re-enable it piecemeal.

## Findings

| Area | Finding in original code | Risk | Remediation in this change |
| --- | --- | --- | --- |
| Correctness | `routes/api.py` synthesized yesterday's predictions/results and wrote them to `predictions`, `game_results`, and `model_metrics`. | Critical: fictitious performance | Endpoint retired; no active route creates outcomes. |
| Models | NBA/MLB/NFL predictors initialize and train from random arrays; reported accuracy is in-sample-like random splitting. | Critical: invalid model claims | Added chronological backtest contracts, calibration, Brier/log loss diagnostics, and model approval metadata. |
| Data | NBA uses a hard-coded 2024–25 table; MLB/NFL return sample games; injury effects are random; ESPN uses HTTP. | Critical: stale/fabricated and insecure inputs | Provider-neutral timestamped contracts, a concrete The Odds API v4 pregame parser, live-event filtering, quota metadata, and no sample fallback. |
| Odds | ESPN-shaped odds are not a multi-book, timestamped market ledger; no overround treatment or line history. | High | Added validated odds conversions, de-vig utility, append-only `odds_snapshot`, and quote idempotency. |
| Backtests | No actual backtest; `/simulate_predictions` uses known results to create predictions. | Critical: look-ahead bias | `run_backtest` enforces chronological decision order and feature/quote availability. |
| Calibration | No calibration or proper scoring rules; “confidence” is ad hoc. | High | Isotonic calibration plus Brier, log loss, and reliability bins. |
| Risk | Risk uses unsupported proxies, can suggest parlays, and caps are not portfolio state. | High | Fractional Kelly is bounded by per-stake, per-event, and daily exposure; stale/unapproved inputs reject. |
| Persistence | `db.create_all()` creates no reviewed schema/migrations; tracker uses raw psycopg tables not declared by the app. | High | Added versioned PostgreSQL audit schema and append-only triggers. |
| Security | Default `dev_secret_key`, debug server bound to all interfaces, verbose logging, and no API auth/rate limiting. | High | Production config requires secrets, DB/Redis and API key; non-debug loopback dev server; headers and request IDs. Rate limiting/WAF remains deployment work. |
| Tests/deps | No tests; tracked `__pycache__`; 1,147-line generated dependency source list, heavyweight unused TensorFlow/OpenAI/Twilio. | High | Clean project metadata, deterministic tests, CI configuration, and no imports of unneeded ML/LLM clients. |
| Operations | No worker boundary, monitoring, backup/restore plan, CI/CD, or deployment architecture. | High | Container, compose topology, scheduled worker hooks, and deployment runbook added. |

## What the code now guarantees—and does not

It guarantees explicit math, input validation, predictable rejection, and an
audit-friendly schema. It does **not** establish an edge, ingest a live feed,
train a real model, settle events, place bets, or make a profitability claim.
Those capabilities require licensed data, an implementation of provider adapters,
and evidence from a locked time-based evaluation.

## Required next engineering increments

1. Connect the The Odds API adapter to a transactional PostgreSQL repository and
   dead-letter/data-quality path. Contract separate providers for results,
   injuries/lineups, and historical data as the product scope requires.
2. Build canonical event/team/player identity mapping and source payload storage
   before modeling.
3. Create feature definitions with `available_at` timestamps. Materialize only
   point-in-time features, then train a simple baseline before complex ensembles.
4. Add a model registry job that persists immutable artifacts, data cutoffs,
   feature schema hash, out-of-fold calibration, and a human approval record.
5. Implement results settlement and daily reconciliations; separately report
   probability metrics, realized return, CLV, void/push handling, and data gaps.
6. Delete or move the legacy prototype only after its replacement has production
   parity and an archival tag exists.
